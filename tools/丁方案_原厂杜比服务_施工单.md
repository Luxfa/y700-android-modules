# 丁方案施工单：装回联想原厂杜比服务（y700_dolby_daxservice）

状态：**首轮实测判负，已回退（2026-11-24 23:32 安全态复验通过）**。判负原因是"联想签名"这道墙，不是音频本身——详见 `04_日志与分析/操作流水账.md` §四十五。
作者：hutao ｜ 依据：`02_调研/20261124_喇叭音效现状排查.md` 第二十二节

## 〇、首轮结论（先读这段，别照下面的步骤再跑一遍）

1. **`INTERACT_ACROSS_USERS_FULL` 的保护级别是 `signature|installer|role|module`，不含 `privileged`** ⇒ privapp 白名单写它也没用（本机实测：`MANAGE_USERS`/`WRITE_SECURE_SETTINGS`/`com.dolby.permission.DAXSERVICE` 都 granted=true，唯独 FULL 没有）。原厂 APK 带的是联想签名 `523324ac`，ColorOS 平台密钥不在手上 ⇒ **不改包、不伪造签名的前提下这条路封死**。实测表现：daxService 开机后约每 0.35 秒崩一次（累计 977 次 SecurityException）。
2. **本单原稿把禁用标记写成 `disabled`，那是无效文件名**；Magisk 认的是 `disable`（另有 `remove`、`skip_mount`）。因为这个错误，21:47"已回退"的 `y700_dolby_bridge` 在 23:18 重启后自行复活，导致首轮同时存在两个杜比创建方 ⇒ **首轮那批稳定性数据（含 tombstone_16 的 DAPV3=3）不能用来判定原厂路径好坏**。
3. **没有被证伪的是"原厂挂载形态"本身**（全局混音单实例 + 应用自持生命周期 + 音频服务看门狗）。若要继续，方向是自写极简常驻服务复刻这三点，`MODIFY_AUDIO_SETTINGS` 即可，不需要特权签名——但要不要做，等用户裁定。

## 一、这次改什么（一句话）

把联想原厂 ZUI 里的杜比服务四件（APK + 授权文件 + 三个系统库）以 **KernelSU/Magisk 无感模块（magic mount）** 的方式盖回系统，
让**原厂自己的服务**用它自己的方式创建杜比效果；**不写任何分区、不改 vendor 文件、不碰 00_救生包/产出**。

## 二、装进去的四件（全部来自官方原包，指纹已记入 05_备份索引）

| 目标路径 | 来源 | 字节 |
|---|---|---|
| `/system_ext/priv-app/daxService/daxService.apk` | ZUI super_6（system_ext_a） | 3,495,554 |
| `/system_ext/etc/permissions/com.dolby.daxservice.xml` | 同上 | 877 |
| `/system/lib64/libdolbyeffect.so` | ZUI super_4（system_a） | 996,008 |
| `/system/lib64/libdolbyproxyandroid.so` | 同上 | 268,808 |
| `/system/lib64/libdolbyui.so` | 同上 | 52,456 |

外加 `service.sh`：开机 `boot_completed` 后等 15 秒，用 root 拉起服务
（`am start-service -a com.dolby.daxuser.DaxService -n com.dolby.daxservice/.DaxService`，重试 5 次），日志写 `/data/local/tmp/y700_dolby_daxservice.log`。

> 首轮实测补正：`/system/lib64/` 那三个库（`libdolbyeffect.so`/`libdolbyproxyandroid.so`/`libdolbyui.so`）在进程存活期间 **maps 里一条都没加载**——它们是杜比设置界面（UI/桥接）用的，服务本体不需要。若日后复用本模块，这三件可以去掉，只留 APK + 授权 xml。

## 三、为什么这样挂不会重演上次的崩溃（依据，不是愿望）

1. 原厂是**全局输出混音单实例**（dex 原文 `Creating a DolbyAudioEffect to global output mix!`），不是上次配置法造成的"按会话各建一份"。
2. 原厂自带 `AudioServerWatchDog`：音频服务一起来就 `dolbyAudio.release()`，需要时再 recreate ⇒ **销毁时机由应用掌控**，不会让框架在会话销毁时去 close 一个叫不醒的工作线程。
3. 同一套 vendor 杜比库在原厂 ZUI 上长期运行不崩 ⇒ 原厂形态是被验证过的安全组合。

**仍然不能保证**：底层还是那个 `libswdapaidl.so`，一次性死等的缺陷仍在库里。所以验收必须三类场景全覆盖（见第五节），任一类崩立刻回退。

```bash
# 0) 前置：确认设备在安全态（杜比配置挂载=无、旧模块 disabled）
adb -s 192.0.2.10:5555 shell "su -c 'md5sum /vendor/etc/audio/sku_canoe/audio_effects_config.xml; ls /data/adb/modules/y700_dolby_bridge/ | tr \"\\n\" \" \"'"

# 2) 打包成可刷入 zip
cd 03_脚本与模块/modules && zip -r ../../临时存档/y700_dolby_daxservice_v1.zip y700_dolby_daxservice -x "*.git*"

# 3) 推到设备并安装（KernelSU 命令行安装，等价于在 App 里"从存储安装模块"）
adb push 临时存档/y700_dolby_daxservice_v1.zip /data/local/tmp/
adb shell "su -c 'ksud module install /data/local/tmp/y700_dolby_daxservice_v1.zip'"

# 4) 重启一次生效（这是唯一必须重启的一步）

```

## 五、验收（三类场景全覆盖，缺一类不得宣布可用）

| 场景 | 动作 | 通过判据 |
|---|---|---|
| 长播放 | 音乐/视频连续播 ≥5 分钟 | `pidof audioserver` 不变、`/data/tombstones` 无新增 |
| 高频切流 | 抖音连续刷 ≥3 分钟（设备自刷，避免采样污染） | 同上；且 `DAPV3` 线程数恒 ≤1 |
| 静置空闲 | 亮屏静止 2 分钟 + 息屏 2 分钟 | 同上；无 `TimeCheck timeout` |

同时取证：`dumpsys media.audio_flinger` 里 DAP 是否挂在 session 0、`settings get global dolby_dap_profile` 是否被服务写值、杜比服务日志。

## 六、回退（一条命令，分区零改动）

```bash
# 只打禁用标记（**文件名必须是 disable，写成 disabled 没有任何效果**），然后重启；不要在运行中 kill 杜比服务
adb shell "su -c 'touch /data/adb/modules/y700_dolby_daxservice/disable'"
adb reboot
# 或走统一回滚：03_脚本与模块/y700_rollback.sh（已把本模块加入 MODS，分支只打 disable 标记并保留目录）
# 复验判据（不是"文件存在"，而是运行态归零）：
adb shell "su -c 'cat /proc/mounts | grep -ac audio_effects_config; ls /system_ext/priv-app/daxService/ 2>&1; pm list packages | grep -ac dolby'"
#    期望依次：0 / No such file / 0
```

**回退为什么不能直接 kill 服务**：杜比效果对象的生命周期挂在创建它的应用进程上。运行中强杀 `com.dolby.daxservice`
会让框架在 binder 死亡回调里去 close 这个效果，而那正是上次崩溃的同一销毁路径（`libswdapaidl.so` 里的一次性死等）。
所以**中途要停也必须走"打 disabled 标记 + 重启"**，由关机流程统一收，绝不图快 kill。

## 七、顺带要做的两件小事（同一次重启里一起验）

1. 旧模块 `y700_dolby_bridge` 保持 `disabled`（配置挂载法已判死，不再启用）；
2. `y700_charge_bridge` 的日志暴露一个功能缺陷（20:27–20:28 每 5 秒重复写 `charging_enabled 1 -> 0` 却始终没生效），
   属充电线，不并入本次，单独排期。
