# 底层打通缺口总表（C17 = 联想底层 + ColorOS 系统层）

状态：**第一轮取证完成（2026-11-25 00:4x）**，可修项已给修法，不可行项写明"为什么不通"，并**撤回我之前的两条错误结论**。
作者：hutao ｜ 取证方式：设备侧只读探测 + 本地官方包离线对照（ZUI 2.5.10.055 与 C17 移植包）

## 〇、先撤回两条我自己讲错的结论（重要，防止后续按错的走）

1. **撤回**："`sys.thermal.enable=false` 把 ColorOS 系统侧温控层关掉了"。
   复核：在 `/system/bin`、`/system_ext/bin`、`/vendor/bin`、`/product/bin` 共 400 个二进制，以及 `services.jar`、`framework.jar`、`oplus-framework.jar` 等框架包里**全量搜 `sys.thermal.enable`，命中数为 0**；`/vendor/etc/init/*.rc` 也没有写它的地方。⇒ 这个键**没有消费方**，它不构成任何开关。发烫报告 §九 里那句结论作废。
2. **撤回**："ColorOS 系统层自带杜比音频（`/product/lib64/libdolbyeffect_5.0.so`、`/system_ext/lib64/libdolbyui.so` 在位）"。
   复核：把这两个库拉到 PC 解字符串，内容全是 **`dolby_vision`、`dolbydpu`、`dolby_conversion_tpb`、`dolbyvision`** ⇒ 那是**杜比视界（视频）**，不是杜比音效。见"三、杜比音效"。

## 一、温控（调度权在谁手里）

| 事实 | 证据 |
|---|---|
| 真正执行降频的是**联想 thermal-engine** | 现场实测：模拟 44℃ → 大核 2880000/小核 1996800；模拟 48℃ → 1017600/384000；撤销立即恢复。策略文件 `/vendor/etc/thermal-engine_*.conf`，场景表 `thermal_user_case.conf` |
| ColorOS 侧**没有可接的温控策略层** | 全分区搜 `*thermal*`：`/product`、`/system_ext`、`/my_product`、`/my_bigball`、`/odm` 里**没有任何 OPLUS 温控策略文件**，只有 `system_ext/etc/obrain/assets/ThermalAgent_*.sql`（统计分析用，不是执行策略） |
| `horae` 在跑但不是温控执行器 | `init.svc.horae=running`、`persist.sys.horae.enable=1`；`/system_ext/etc/init/horae.rc` 显示它 `class hal`、开机后起；运行期只打开 `/sys/kernel/tracing/trace_marker`（性能/追踪引擎），二进制里没有温控策略路径字符串 |
| 温度→帧率的表存在但属 Qualcomm 侧 | `/vendor/etc/display/thermallevel_to_fps.xml`：level1-2→144fps、3-4→120、5-7→90、8-10→60（由显示 HAL 消费，非 ColorOS 系统层） |

⇒ **结论：用户要的"让 ColorOS 来调度温控"在现有套件里做不到**——ColorOS 的温控策略文件没随 C17 包进来，执行权天然在联想 thermal-engine。现实可做的只有两类：① 继续用模块改 thermal-engine 阈值（已做，`y700_thermal_tune`）；② 拿到同架构真 ColorOS 机的温控策略文件再搬（当前无来源）。

## 二、刷新率 / 高帧（这是真缺口，可修）

| 键 | ZUI 原厂 | C17 现场 | 判定 |
|---|---|---|---|
| `ro.surface_flinger.use_content_detection_for_refresh_rate` | **true** | **false** | **唯一被改掉的帧率键 ⇒ 头号嫌疑犯** |
| `ro.surface_flinger.game_default_frame_rate_override` | 60 | 60 | 两边一致，不是移植造成的 |
| `ro.surface_flinger.enable_frame_rate_override` | false | false | 同上（联想不走"按应用覆盖"这条路） |
| `debug.graphics.game_default_frame_rate.disabled` | 1 | 1 | 同上 |

配套事实（都已实测）：
- 面板模式表齐全：`supportedModes` = 30/60/90/120/144/165 六档；`defaultModeId` 指向 60Hz 档。
- 系统投票允许到 165：`PRIORITY_USER_SETTING_PEAK_RENDER_FRAME_RATE → mMaxRefreshRate=165`，`user_refresh_rate=165`、`peak_refresh_rate=165`。
- ColorOS 的帧率服务**认得出游戏**：`VRR[OPlusRefreshRateService]: setGameBattleStatus: true, com.tencent.tmgp.pubgmhd`，且日志显示它切过 `configId:4`(90Hz) 与 `configId:3`(144Hz)。
- 但 `mDisplayModeSpecs` 里 **render 区间被写成 (0, 60)**，游戏层 `app duration=16666666ns`＝60Hz 节拍；`FrameRateOverrides=none`、`Override: off`。
- 机型白名单是第二个候选原因：C17 全盘上报 `OPD2511 / OPPO / OP6546L1`、`ro.product.marketname` 为空；而 ZUI 原厂 vendor 写的是 `ro.product.model_for_attestation=TB323FU`、`brand_for_attestation=Lenovo`。腾讯 90/120 帧按机型放开 ⇒ **改机型触碰"不伪造机型身份"红线，未做，需单独裁定**。

⇒ 修法（已备好未装）：`y700_fps_unlock` 模块，`system.prop` 只写一行 `ro.surface_flinger.use_content_detection_for_refresh_rate=true`。判据：游戏内 `dumpsys SurfaceFlinger --latency <现取层名>` 的周期从 16666666ns 变 11111111ns（90Hz）。

## 三、杜比音效（这条路在现有件上不通，必须说清）

| 检查项 | 结果 |
|---|---|
| ColorOS 系统分区里有没有杜比**音频**客户端 | **没有**。全分区搜 `*swdap* / *dlb* / *dax* / *atmos*` 在 `/product`、`/system`、`/system_ext`、`/my_product`、`/odm` 命中 0（只有 `libhidlbase.so` 这种假匹配）；`framework.jar`/`oplus-framework.jar` 里没有 `DolbyAudioEffect` 类 |
| 音效中心里剩下什么 | 只有配置键名：`dolby_support_apps`、`dolby_multi_config`、`dolby_geq_on_off`、`dolby_for_engineering`、`dolby_category`（没有实现体，也没有杜比 UI 资源字符串） |
| 当前生效的音效套件 | `ro.oplus.audio.effect.type=audiox_merge`、`oplus_customize_dirac_sound_effect=1`、`ro.audio.spatializer_type=oplus`；设置→声音→音效页显示 **OReality 音效**（智能/沉浸/保真/自定义） |
| 运行时改 `effect.type=dolby` 试试 | `resetprop` 改成功并重启音效中心与设置，**UI 仍是 OReality**，没有出现杜比分支（因为实现体压根不在包里） |
| vendor 侧（联想）杜比音频件 | 齐：`/vendor/etc/dolby/dax-default.xml`、`libswdapaidl.so`、DMS 服务、`ro.vendor.dolby.dax.version=DAX3_3.14.0.10_r1` |

⇒ **结论：杜比音效无法"通过 ColorOS 系统层打通"**，因为 ColorOS 这一半的实现体不在这套件里。剩余可选路径只有两条，都不是"打通"而是"自建"：
- **丁2**：自己写一个极小的常驻服务，用标准 `AudioEffect` API 按 DAP UUID（`9d4921da-8225-4f29-aefa-39537a04bcaa`）在**全局输出混音 session 0** 上建**单实例**、并自管生命周期（复刻原厂的 `AudioServerWatchDog` 释放/重建）。不需要任何签名特权。风险：底层仍是那个有"一次性死等"缺陷的 `libswdapaidl.so`，必须三类场景全覆盖验证。
- **放弃外放杜比**：保留 OReality/Dirac（现在就是能用的那套）。

## 四、其余待查项（本轮未动，列出来避免遗漏）

- `ro.config.lgsi.default_refreshrate=165` 及其 `reading_mode_require_fps`/`aod_require_fps`/`low_power_mode_require_fps`：C17 上无消费方（联想 LGSI 专属），属"底层策略在、系统层不认"，但**改它没有收益来源**，优先级低。
- `y700_charge_bridge` 的 `charging_enabled 1 -> 0` 每 5 秒重复写却不生效：功能缺陷，单独排期。
- `thermallevel_to_fps.xml` 的消费方与是否真在按温度降帧：需要一次温度拉高后的实测（与帧率项联动）。
