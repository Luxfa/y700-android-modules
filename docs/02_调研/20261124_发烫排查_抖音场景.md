# 发烫排查（2026-11-24 22:4x–23:2x）· 抖音场景

用户报障："为什么刷抖音平板都发烫？是不是移植和底层有什么没打通、没打好？"
本节只讲**测到的数**与**已定位的嫌疑**，最后给结论与方案。设备全程只读或可逆（帧率设置已复原，未装任何新模块）。

## 一、先纠正我自己造成的测量污染

第一版采样脚本每 2 秒调一次 `dumpsys display` + `top` + `dmesg`，全走 WiFi adb。
**静默 75 秒不做任何查询后，`user_temp` 从 40.3℃ 掉到 36.2℃、电流从 880mA 掉到 88mA。**
⇒ 采样本身在加热设备。之后所有数据改用"只读 sysfs"的轻量采样，并进一步改成**设备自己刷流自己采样、PC 只在结束后读一次**（`heat_selftest.sh`）。凡与此前口径不同的数，以轻量版为准。

## 三、四条"没打通"的直接证据

1. **ColorOS 的温控总开关是关的**：`[sys.thermal.enable]: [false]`。
   同时 `dumpsys thermalservice` 显示 `Thermal Status: 0`，而它缓存的 `CPU0=99.6℃`（裸 die 温度）——**系统侧不据此做任何降频/限帧决定**。
   实际在管温度的只有联想 vendor 侧的 `thermal-engine`（`init.svc.thermal-engine=running`）与标准 `IThermal`，其阈值是 `[48,49,50,60,61,90]`（壳温 48℃ 才动）。**41℃ 这个区间没有任何一层在收频。**

2. **壳温数据源在 ColorOS 侧是瞎的**（这条与既有结案结论有关，需要用户重新裁定）：
   总账 §十二之前裁定"`horae` 壳温不动也不修"，理由是 OPLUS 系统层要私有节点 `/proc/shell-temp`，联想 043 内核没打这个补丁，`horae` 恒报 34.1℃，当时判定"只影响读数、不影响内核降频"。
   **本次新证据把影响面扩大了**：ColorOS 的场景档（Midas）与系统侧温控都以这个读数为输入，读数恒 34.1℃ ⇒ **系统侧永远不会因为"烫"去降帧降频**；真实壳温在 `thermal_zone55/56/58/59`（front/back/user_front/user_back），41℃ 就在这些节点上。
   ⇒ 这条是否重开，请用户裁定（不擅自开工）。

3. **恒定 165Hz、没有空闲降帧**：`mDisplayModeSpecs` 里 `idleScreenRefreshRateConfig=null`、`hasArrSupport=false`、`ro.surface_flinger.use_content_detection_for_refresh_rate=false`、`HWVsyncSuppressed: off`。
   对照原厂：ZUI `system/build.prop` 里 `ro.config.lgsi.default_refreshrate=165`（**原厂默认也是 165，所以"高刷本身"不是移植带来的退化**），但原厂还带一整套 lgsi 帧率策略：`reading_mode_require_fps=30`、`aod_require_fps=30`、`low_power_mode_require_fps=60`、`surface_flinger.available_refreshrates=30_60_90_120_144_165`。
   **C17 的系统层是 ColorOS，没有任何组件读这些 `ro.config.lgsi.*` 属性**（属性在联想 vendor/system 里，消费方在联想 system 里）⇒ 这套"该降就降"的帧率策略在 C17 上是死的。
   实测代价：仅把帧率压到 60Hz，`crtc_commit` 的 CPU 占用就从 35% 降到 3.4%。

4. **ColorOS 侧有组件在反复找不存在的联想底层服务**：`dmesg` 里每分钟几十条
   `avc: denied { find } ... name=vendor.oplus.hardware.gameopt.IGameOptHalService/default scontext=u:r:oiface:s0`（约每 30 秒一次重试）；另有 `droid.ugc.aweme` 反复读 `qemu_hw_prop` 被拒（抖音自己的反模拟器探测）。
   `dmesg` 里 `avc: denied` 累计 **119 条/尾部窗口**、events 缓冲 **550 条** ⇒ 审计与 logd 一直在忙（不是主要热源，但属"没打通"的实证）。

## 四、挂起（sleep）侧的观察，尚需干净复测

息屏时看到 `PM: suspend entry (s2idle)` 与 `suspend exit` 每隔 1–2 秒成对出现，且有一次
`Freezing user space processes aborted after 0.030 seconds (2209 tasks refusing to freeze, wq_busy=0)`。
⇒ 疑似"挂起风暴"：设备其实没真正睡下去。
**但这一条与我的 adb 轮询强相关（WiFi adb 每 2 秒唤醒一次）**，必须在无 adb 流量的条件下复测才能定论；同时息屏底噪功耗 0.71–0.76W 属"偏高但不离谱"，所以挂起风暴目前只算**待验嫌疑**，不作为结论。

## 五、帧率 A/B（同条件连续刷流各 60 秒，设备侧自刷自采）

| 帧率 | 功率中位 | 区间 | 抖音 CPU（单核算） | load |
|---|---|---|---|---|
| 165Hz | **3.55 W** | 3.34–3.98 | 31% | 6.68 |
| 120Hz | **3.45 W** | 3.27–3.76 | 30% | 6.73 |
| 60Hz | **3.34 W** | 2.90–3.84 | 31% | 6.83 |

⇒ **我先前对帧率的判断被自己的数据推翻了**：真实刷流时 165→60Hz 只省 **0.21W（约 6%）**，抖音 CPU 与 load 几乎不变。
⇒ 之前"60Hz 下 `crtc_commit` 从 35% 降到 3.4%"是在**暂停画面**下测的（暂停时 165Hz 仍在持续提交，降帧后提交量骤减）；**一旦真的在刷流，各帧率都要持续出帧，差别就没了**。
⇒ 结论：**帧率不是刷抖音发烫的主因**，只在"亮屏静止"场景有价值（可省 DPU 提交开销）。

## 六、温控为什么"看着不管"——原厂阈值本来就设得很晚（这是原厂的数，不是移植丢失）

从 ZUI 原包 vendor 里取出原厂温控配置（`临时存档/heat_20261124/te/`，出处 `super_7.img`=vendor_a）：

```
thermal_user_case.conf:  场景 0（默认）= sensor_0 + cpu_0 + gpu_0 + fan_0 + common_0 + battery_0
thermal-engine_cpu_0.conf（传感器 quiet-therm）：
  大核 cpu-cluster1:  35℃→4512000(=不限)  43℃→2880000  45℃→1747200  47℃→1017600  49℃→883200
  小核 cpu-cluster0:  35℃→3513600(=不限)  43℃→1996800  45℃→ 998400  47℃→ 384000  49℃→384000
thermal-engine_gpu_0.conf（传感器 quiet-therm）：44℃→902MHz、46℃→646MHz、48℃→539MHz、50℃→222MHz
thermal-engine_common_0.conf：lcm-thermal 55℃ 才限背光
```

实测本机：`quiet-therm = 35.3–36.5℃`（对应内核算出的 **壳温 user_temp 40.3–41.5℃**），
`policy6 scaling_max_freq=4512000`、`policy0=3513600`、GPU 上限 1200MHz —— **全部不封顶，与原厂配置完全一致**。

⇒ **"刷抖音到 41℃ 还不降频"是联想原厂的设计**（介入点 43℃ 起，且用的是 quiet-therm，比壳温低约 5℃，等效壳温约 48℃ 才收频），**不是移植把它改坏了**。
⇒ 但也正因为介入点这么晚，"手感发烫"在 40–42℃ 区间是**没有任何一层在压它**的。

## 七、系统侧温控层在这台机器上确实是关的（这条算移植带来的缺口）

`sys.thermal.enable=false` 的出处查清了：**写在 `/vendor/build.prop` 里**（联想 vendor 侧的设定，原厂 ZUI 也是这个值）。
在原厂 ZUI 上，这个键关掉无所谓——联想系统层有自己的一套；**在 C17 上，系统层换成了 ColorOS，而 ColorOS 的温控层被这个 vendor 属性关掉**，于是：

- 系统侧不会基于壳温做降帧/降频/场景限流；
- 只剩 vendor 侧 thermal-engine 那道"43℃ 起"的晚介入兜底；
- 加上既有结案记录里的那条：ColorOS 的 `horae` 因联想内核没有 `/proc/shell-temp` 节点，**壳温恒报 34.1℃**（总账 §十二 曾裁定"不动也不修"，理由是只影响读数）——但读数正是系统侧决策的输入，**这条的影响面比当时判定的更大，是否重开请用户裁定，我不擅自动工**。

## 八、其余已定位项（量级都不大，但都是"没打通"的实证）

- `oiface` 每约 30 秒重试找 `vendor.oplus.hardware.gameopt.IGameOptHalService/default` 被拒（联想底层没有这个 HAL）；`dmesg` 尾部窗口 `avc: denied` 119 条、events 缓冲 550 条 ⇒ 审计与 logd 长期在忙。
- 抖音自身：暂停时也占 19–48% CPU，刷流时 15–69%（单核算），是最大单一负载。
- 息屏底噪 0.71–0.76W；息屏时仍见大核 4.5GHz 与 `PM: suspend entry/exit` 成对高频出现、一次 `2209 tasks refusing to freeze` —— **待无 adb 流量的干净复测**，暂不作结论。
- 真实 CPU 利用率（静置亮屏 10 秒自算）只有 **11.9%**，而 load 5.7 —— 说明 load 高是**大量内核线程长期处于 D 态等待**（高通平台常态），不是有人在空转烧 CPU。内存也不紧张：`MemAvailable 4.2GB`。

## 九、功耗拆解（设备侧自刷自采，无 adb 流量污染）

| 场景 | 功率中位 | 区间 | quiet-therm | load |
|---|---|---|---|---|
| 亮屏静止（已杀抖音，桌面待机） | **2.34 W** | 2.04–4.63 | 34.8→34.1℃ | 5.76 |
| 亮屏 + 设备自动刷抖音 60 秒 | **3.82 W** | 1.96–4.44 | 36.4→35.9℃ | 5.29 |

⇒ **抖音这一路视频 + 网络 ≈ 1.5 W 增量**，剩下 **2.3 W 是"亮屏基础开销"**（本次亮度 1046/4095 ≈ 26%）。
⇒ 真实 CPU 利用率（静置亮屏，10 秒自算）只有 **11.9%**，load 5.7 是高通平台大量内核线程长期 D 态的常态，**不是有人在空转烧 CPU**；内存也不紧（`MemAvailable 4.2GB`）。

## 十、总判断（回答"是不是移植没打通"）

**发热本身的主因不是移植缺陷**：3.8W 的刷流功耗里 1.5W 是抖音自身，2.3W 是亮屏基础开销；帧率只影响 0.2W；温控阈值是联想原厂设的（43℃ 起），原厂机也一样。

**但移植确实留下了三个"该管温度的人不在岗"的缺口**，它们不会让机器更烫的"产热"，但让**该压的时候压不下来**：

1. `sys.thermal.enable=false` 写在 **`/vendor/build.prop`**（联想设定）。原厂 ZUI 不靠这个键；**C17 的系统层是 ColorOS，被这个键直接把系统侧温控层关掉** ⇒ 只剩 vendor 那道 43℃ 起的晚介入。
2. 联想原厂的帧率策略属性（`ro.config.lgsi.reading_mode_require_fps=30`、`aod_require_fps=30`、`low_power_mode_require_fps=60`）在 C17 上**没有任何消费方**（消费方在联想系统层）⇒ 静止/阅读/低功耗场景不会主动降帧。
3. 既有结案记录里那条 **`horae` 壳温恒报 34.1℃**（联想内核没有 `/proc/shell-temp` 节点）：当时裁定"只影响读数、不影响内核降频"，但**系统侧场景决策的输入正是这个读数**，影响面比当时判定的更大。**是否重开这条工作线请用户裁定，我不擅自开工。**

另外两条属于"没打通"但量级很小：`oiface` 每约 30 秒重试找不存在的 `gameopt` HAL；抖音反模拟器探测被 SELinux 反复拒绝（审计与 logd 长忙）。

| 方案 | 做什么 | 预期收益 | 代价 |

## 十二、甲方案（提前收油门）装机后的真实场景数据（2026-11-25 00:0x–00:4x）

| 场景 | quiet-therm 走向 | 是否触发限频 | 实测上限 | 判读 |
|---|---|---|---|---|
| 刷抖音自刷 5 分钟（改后 B 组） | 37.2 → 36.7（峰值 37.2） | 基本没触发 | 大核仍多次跑到 4512000 | 日常负载本来就够不到 38℃，**收益体现在"温度不再往上爬"** |
| 刷抖音自刷 5 分钟（原厂 A 组） | 37.3 → **38.1**（峰值 38.1） | 未触发（原厂 43℃ 才动） | 同上 | 两组功率均值 4.08W vs 4.35W；**温度差 0.9℃ 但方向不同：改后往下、原厂往上** |
| 合成满载（8 线程 dd，改后） | 39.1 → 40.2（12 秒内） | **立刻触发** | 39.1℃→大核 2880000；40.2℃→1747200 | 阶梯在真实发热下确实介入，功率 7.5–11.9W |
| 和平精英 训练场（改后） | 00:23 已到 **38.9℃** | **已触发** | 小核 998400、大核 1747200（原厂此时不限） | **甲方案对游戏有实伤，已量化** |

结论：提前收油门**对"日常刷视频不发烫"有效**（温度曲线被压平），但**38℃ 这一档对游戏太早**。可选处理：
① 收窄到 CPU 41℃ 起、GPU 回原厂 44℃ 起（日常仍受益，游戏多 3℃ 余量）；
② 保持 38℃，游戏前手动切回原厂（每次要重启一次，麻烦）；
③ 撤销甲方案。
