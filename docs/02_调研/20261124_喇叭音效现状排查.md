# 喇叭音效现状排查（2026-11-24，全程只读，设备零改动）

## 一、一句话结论

硬件是**双扬声器 + Awinic AW882xx 智能功放**，立体声链路在 framework 侧完整、没有被下混；但**软件音效这一层基本是空的**——ColorOS 系统层声明的 AudioX 音效在联想底层没有实现载体，系统层与底层的效果名还错配，实测 8 条音频输出线程里 7 条一条效果链都没挂。当前外放听到的声音，本质上是"联想原厂调音直出，没有 ColorOS 音效加成"。

## 二、发声链路：谁在响

| 环节 | 实测事实 | 证据 |
|---|---|---|
| 声卡 | `canoe-qrd-snd-card`（高通 QRD 参考设计变体） | `01_声卡与PCM设备清单.txt` |
| Linux 侧 codec | 只有 `lpass-cdc` 与 `wcd939x` 两个 | `02_codec与I2C设备.txt` |
| 功放芯片 | I2C 上 **两颗** `aw882xx_smartpa`（Awinic 智能功放，左右各一） | `02_codec与I2C设备.txt` |
| 振动马达 | `haptic_hv_l` + `haptic_hv_r`（左右双马达，与双扬声器同布局） | 同上 |
| 高通 WSA884x 智能功放 | **未注册**：不在 codecs 里，dmesg 无记录，ALSA 324 个控件里没有任何 spk/amp 控件 | `03_ALSA控件全量_324项.txt` |
| 物理布局判定 | **确实是立体声双扬声器**，不是单喇叭 | 综合上四行 |

要点：本机功放**不走高通 WSA 那套**，而是外挂 AW882xx。功放自带 DSP，控制面在 ADSP/I2C（`glink-i2c` 在位），Linux 的 ALSA mixer 层看不到它，所以 `tinymix` 里查不到扬声器控件属正常，不是故障。

## 三、通路配置：有一处明显缺口

`/vendor/etc/audio/sku_canoe/mixer_paths_canoe_qrd.xml` 里：

```xml
<path name="speaker">
</path>                    ← 立体声外放通路是空的

<path name="speaker-mono">
    <ctl name="WSA PCM CH1 MUX" value="AIF_PCM_PB" />
    <ctl name="SA1 Rx Channel Select" value="CH1" />
    <ctl name="SA1 FU21 Stereo Gain Offset dB" value="72" />
</path>                    ← 只有单声道通路写了参数，而且写的是高通 WSA/SA1 图控件
```

- **`speaker` 通路为空**：立体声外放在 ALSA mixer 层没有任何专属配置，实际出声完全依赖 ADSP 侧图形 + 功放自身 DSP。原文见 `06_qrd扬声器通路定义.txt`。
- **残留不匹配**：`mcs_defs_canoe_qrd.xml` 里仍有 `WSA`/`WSA2` 图单元各 2 处，而本机并没有 WSA 功放注册；`speaker-mono` 的增益参数（72/84）是给高通智能功放写的。这说明这套配置是**参考设计模板**，不是按本机 AW882xx 精调的。
- ACDB 调音库有两套 QRD：`canoe_qrd` 与 `canoe_qrd_wsa884x`（`/vendor/etc/acdbdata/` 共 18 个项目）。EQ / 限幅 / 智能功放保护参数都在 ACDB 里，本机命中的是 qrd 非 wsa884x 那一套——**这套调音是联想按自己硬件出的，不是 ColorOS 的音色**。
- AW882xx 侧只找到 `aw882xx_acf.bin`（1792 字节，纯寄存器配置）和校准工具 `/vendor/bin/aw882xx_cali`，**没有找到大体积的功放调音/波形文件**；`caldata` 节点读不到内容。⇒ 功放曲线是否已逐机校准，**未定论**。

## 四、音效层：ColorOS 想加的音效没有落地（结构性缺口）

系统层（ColorOS）声明的能力：

```
ro.oplus.audio.effect.type            = audiox_merge
ro.oplus.audio.effect.speaker_geq     = true    ← 扬声器图形均衡
ro.oplus.audio.effect.high_quality    = true    ← 音质增强
ro.oplus.audio.speaker_clean          = true    ← 智能清音
ro.oplus.audio.support.low_latency_game         = true
ro.oplus.audio.support.low_latency_game_effect  = false   ← 底层不支持
ro.oplus.audio.support.low_latency_game_effect.show_ui = true  ← 但 UI 照样显示
```

底层（联想 vendor）实际提供的：`/vendor/lib64/soundfx/` 共 22 个库，全是 AOSP + 高通（`libqcompostprocbundle` / `libquasar` / `libdynproc` / `libvolumelistener` …），**没有任何 OPLUS AudioX 效果库**；vendor `audio_effects.xml` 声明的 `libasphere.so` 文件**不存在**；4 个 OPLUS 音频 HAL（bluetooth_audio_extend / camera_audio / virtual_device.audio）未注册。

两处引用错配（实测核对）：

```
/system/etc/audio_effects.xml 里：
  music_post_proc         vendor未定义  system未定义  ← 悬空
  voice_post_proc         vendor未定义  system未定义  ← 悬空
  notification_post_proc  vendor未定义  system未定义  ← 悬空
底层实际给的效果名是另一套：music_helper / ring_helper / alarm_helper / voice_helper / notification_helper
```

⇒ **系统层想挂到"音乐/通话/通知"三条流上的默认后处理，名字对不上，装配失败。**

运行时印证（`dumpsys media.audio_flinger`）：

```
输出线程 8 条   其中 0 Effect Chains 的 7 条   有效果的 1 条
唯一那条挂的是 Effect ID 8043 = "Music Volume Listener"（Dolby）——只听音量，不塑形
```

⇒ **当前外放链路上没有任何有实质作用的软件音效在跑。** 这与显示色彩那边"4 个 OPLUS 色彩 HAL 缺口 + 效果名错配"是同一个结构性问题的另一面：系统层要的东西底层没提供。

Dolby 与空间音的资产情况：`system_dolby_geq_state=1`（键是开的）、`media_codecs_dolby_audio.xml` 与 `IComponentStore/dolby` 在位，但 Dolby 音频**效果**没进输出链；`ro.audio.spatializer_type=oplus` + `libspatializerRender.so` 在位（耳机/空间音路径可用性与外放无关）。

## 五、立体声有没有被下混？——没有，这条可以排除

| 检查点 | 实测值 |
|---|---|
| 主输出线程 `AudioOut_D` 声道 | `Channel count: 2`、`Channel mask: 0x00000003 (front-left, front-right)` |
| 同线程 Mixer channel Mask | `0x3 (front-left, front-right)` |
| HAL 侧 profile | `low_latency_out` / `deep_buffer_out` / `raw_out` 全部 `channelLayouts="LAYOUT_STEREO"` |
| 8 条线程的声道掩码 | 全部 `0x3` 立体声，无一条 mono |
| 单声道强制 | `Master mute: off`；`accessibility_audio_mono`、`master_mono` 均为空（未开） |

我早前把 dump 里的 `monoPipeWritten == framesWritten` 当成"疑似下混"的线索，现在更正定性：那是厂商埋点的**管道计数**（同线程还有 `PipeSink frames written`），在本机 HAL 与 mixer 都是立体声的前提下，**不能读成"立体声被压成单声道"**。framework 层的立体声是完整的。

## 六、音量与响度

- `/vendor/etc/audio_policy_volumes.xml` 是 **AOSP 通用文件**，扬声器类目引用 `DEFAULT_DEVICE_CATEGORY_SPEAKER_VOLUME_CURVE` ⇒ 用的是 AOSP 默认扬声器曲线，不是逐机精调曲线（ColorOS 原机会带精细分段曲线）。
- 运行时音乐音量在满档：`volume_music=100`、`volume_music_speaker=4160`、`volume_alarm=12`、`volume_voice=5`。
- `media.stagefright.audio.deep=false`：无 deep buffer 输出通路的低延迟优化开关处于关闭态（外放延迟表现的一个变量，未测实际延迟）。

## 七、未定论清单（不下结论，避免误导）

1. AW882xx 两颗功放**是否做过逐机校准**、校准参数在哪——文件层面没找到，`caldata` 读不到。
2. `<path name="speaker">` 为空是**有意为之**（全交给 ADSP 图）还是移植遗漏——无法只靠静态文件判定，需要 ADSP 侧图日志（`/data/vendor/audio/acdbdata`、`audio_feature_stats`）或高通 QACT 才能确认。

4. `audio.spatializer` 与外放是否有耦合——未测。

## 八、需要用户主观判定的三项（不改设备，只测耳朵）

这三项机器测不出来，必须人耳判：

- **左右是否都响**：找一首有明显左右声像移动的立体声曲子（例如飞机从左扫到右），横握平板，听两个方向是否都有声。**若只有一侧响，说明通路有断点，那是硬件/配置问题而非音色问题。**
- **满档是否有破音/削顶**：音量拉满放一段人声+鼓点，听高音处是否发刺、发破。ACDB 限幅是联想自己出的，理论上安全，但要耳朵确认。
- **低频量感**：与小尺寸双扬声器的物理预期对比——如果觉得比原系统薄，最可能的原因就是第四节那条"AudioX 音效没有落地"。

## 十一、对"系统不处理声音"这个方案的评估（结论：方向不对，但不是不能做）

1. **"让系统不处理"现在已基本是事实**：音乐流上没有 ColorOS 音效在加工（悬空引用装配失败 + 7/8 线程无效果链）。再往下减，只剩安卓框架自己的音量曲线与混音——这两步在 AudioFlinger 里，**属于必经环节，绕开需要改 vendor 的音频 HAL 或换策略配置，属高危不可逆方向，不建议**。
2. **用户真正想要的"原厂声音"不在"减处理"这一侧，而在"加杜比"这一侧**：原厂调教 = 联想 ACDB（已经生效，在 ADSP 侧）+ 联想 DAX3 杜比（在位但没挂）。所以正解是**把杜比接上**，不是把系统处理拆掉。
3. **代价（需用户知情）**：挂上杜比后音乐通路多一级处理，会有处理延迟；游戏听声辨位的方位感可能变化（有人更准、有人觉得糊）；响度与低频会上来。**设置里可随时关，零分区改动，完全可逆。**

## 十二、实测判决：设置里的"音效设置"页现在是摆设（20:21，用户开页面时实时抓日志）

用户进入 **设置 → 声音 → 音效设置**（截图：当前播放设备=扬声器，音效=**OReality 音效**，模式=**自定义**，可选 智能/沉浸/保真/自定义）。

同一时刻日志抓到**决定性失败**（300 秒窗口 20:19:30–20:25:03 内 **111 次**，约每 2.7 秒一次；原文 `09_音效页杜比创建失败_logcat.txt`）：

```
AudioEffect: set(): AudioFlinger could not create effect
    41f6c0f4-5d8f-11ec-bf63-0242ac130002 / 41f6c0f4-5d8f-11ec-bf63-0242ac130002, status: -2
AudioFlinger: createEffect() error -2 from getEffectDescriptor
AudioFlinger: createEffect pid 6952 ... sessionId 0, io 0
```

- 发起方 `pid 6952 = com.oplus.persist.multimedia`（ColorOS 常驻多媒体服务），`sessionId 0` = 想挂到**全局扬声器输出**。
- `status -2 = ENOENT`：效果工厂里**没有这个 UUID 的条目**。效果工厂本身是在册的（`android.hardware.audio.effect.IFactory/default`，QTI 声明 version 3）。
- 也就是说：**ColorOS 的 OReality 音效（走杜比实现）在联想底层没有注册入口，界面怎么点都挂不上。**

**但底层另有一条已经注册好的杜比入口，两边名字对不上**：

```
/vendor/etc/audio/sku_canoe/audio_effects_config.xml:
    <library name="dap" path="libswdapaidl.so"/>
    <effect name="dap" library="dap" uuid="9d4921da-8225-4f29-aefa-39537a04bcaa"
            type="fa81de0e-588b-11ed-9b6a-0242ac120002"/>
    （DAP = Dolby Audio Pipeline，高通 PPM 给杜比 DAX3 用的效果入口，联想已声明）
```

⇒ **根因定型**：不是"底层没有杜比"，也不是"服务没起"（DMS 在跑、`IDms` 在册、`dax-default.xml` 在位），而是 **ColorOS 要的效果 UUID（`41f6c0f4…`）与联想底层提供的效果 UUID（`dap / 9d4921da…`）不是同一个，系统层调不到它**。这与色彩那 4 个 OPLUS HAL 缺口、`music_post_proc` 悬空引用属**同一类移植错配**，至此音频侧证据链完整。

**顺带确认一件对用户有利的事实**：正因为挂不上，**当前外放就是"系统不加工、联想原厂 ACDB 直出"** —— 用户想要的"系统不处理声音"这一半，天然已经成立；剩下的分歧只在"要不要把原厂杜比接进来"。

### 14.1 原设想为什么做不到：ColorOS 要的效果在本机没有实现体

拉回四个库逐个解析 ELF（脚本 `临时存档/audio/dolbyfx/elfscan.py`，纯 Python 手解 ELF64，本机无 readelf/objdump）：

## 十七、方案作废：杜比挂载触发音频服务崩溃循环（21:39–21:47，事故实录）

### 18.1 abort message 直接给出死法

⇒ **杜比效果的线程销毁函数（`EffectThread::destroyThread`）出现在 HAL 崩溃栈里**；同时 PAL 走到 `ssrHandlingLoop`（SSR = ADSP 子系统重启处理）。合起来读：**销毁杜比效果线程这条路径在 C17 上会把 vendor 音频 HAL 一起带崩**，HAL 崩了，audioserver 那边等待关闭的 binder 调用自然永不返回。

- **不是配置写坏**：同一份配置在 20:46–21:33 音乐应用下实测正常（`Effect ID 147 name: DAP`、`process()` 持续增长、无崩溃）。
- **不是档位/重载方式**：首次崩溃 21:39:36 **早于**桥的两次自动触发（21:41:39、21:41:51）。

### 18.5 可行性判定（结论）

| 路 | 判定 | 依据 |
|---|---|---|
| 把 DAP 挂成**音乐流后处理效果**（本方案） | **不可交付** | 后处理效果随会话生灭；抖音这类"高频停止会话"的应用必然反复走 `destroyThread`，命中崩因 |
| 改成**只在开机创建一次、不随会话销毁**的全局效果 | 配置做不到 | 该生命周期由框架管理，`<postprocess>` 天生就是会话级；要常驻得框架或 HAL 侧支持，非挂载可解 |
| 只换档位、不挂效果 | 无意义 | 没有效果实例，杜比不会处理音频 |

⇒ **杜比这条"绕开页面"的路在 C17 上被判死**，除非后续能证明崩溃只在特定格式/采样率下发生（那需要复现采集，属丙阶段，且要用户让出设备）。当前设备状态保持安全态：模块 `disabled`、配置回原厂、桥监听停止。

## 十九、丙阶段第一轮（离线）：死锁形态看清了——多实例 + 无人唤醒的 FMQ 等待

读 tombstone_25/27 的**全部线程栈**（不是只看崩溃线程），拿到决定性形态：

```
HAL 内线程名统计：DAPV3 ×2、Music ×2、Dolby ×1，另有 deep_buffer_out / low_latency_out /
                 raw_out_61 / haptics_out_62 / voip_playback_6 / voice_tx_68 等

两条 DAPV3 线程都停在同一处：
  #03 libswdapaidl.so  DapSwEffectImpl::process()+80
  #02 libfmq.so        EventFlag::wait(...)        ← 等框架喂音频数据，无人唤醒
  #04 libswdapaidl.so  EffectThread::threadLoop()+348

另一条 Music 线程停在 condition_variable::wait（libdlbvolaidl.so 的 EffectThread）
```

**读法（这是形态学结论，不是猜因果）**：

1. **同时存在两个杜比效果实例**（两条 `DAPV3` 线程）。⇒ 后处理登记是**按输出会话**创建的，抖音会同时占用多条音乐输出（预加载下一条视频），于是杜比被创建了两份。
2. 这些效果线程的工作方式是**阻塞在 FMQ 的 `EventFlag::wait()` 上等框架喂数据**。
3. 框架销毁效果时走的正是前面定位的 `EffectThread::destroyThread()`，它要**等这条线程退出**；而线程还停在没人唤醒的 `EventFlag::wait()` 上 ⇒ **join 永不返回 ⇒ binder `close()` 卡死 ⇒ audioserver 被 TimeCheck 看门狗杀掉**。

⇒ **性质判定：这是"多实例 + 销毁时无人唤醒"的销毁路径死锁，属集成缺陷，不是杜比算法或原厂参数的问题。** 这也解释了为什么联想原厂 ZUI 不崩、而我们在 C17 上崩：崩的是**框架与效果库之间的生命周期配合**，与音色无关。

**由此得出两条待验假设（丙阶段第二轮要测的就是这两条）**：

- **假设一（实例数）**：崩溃只在杜比实例数 ≥ 2 时发生。若成立 ⇒ 只要限制成单实例就可能安全，值得继续。

### 21.5 机器码级复核（新增，把"为什么"钉死）

手解 ARM64 指令（`临时存档/audio/dolbyfx/calltree.py`：解 `.dynsym` + `.rela.plt` + `.plt` stub，逐条扫 `bl` 目标；再扫 `b` 回边判断等待是否在循环内），两库对比：

| 检查项 | `libdlbvolaidl.so`（销毁只用 1 毫秒） | `libswdapaidl.so`（销毁永不返回） |
|---|---|---|
| `EffectImpl::close()` 里做了什么 | 调 `notifyEventFlag`（→ `EventFlag::wake`） | **同样调** `notifyEventFlag` + `EffectThread::destroyThread` |
| `EffectThread::destroyThread()` | 调 `std::thread::join()` | **同样**调 `join()` |
| 是否重写 `process()` | **没有**（只用基类 `EffectImpl::process`） | **重写了**：`DapSwEffectImpl::process()`（964 字节） |
| 基类 `EffectImpl::process()` 的 `EventFlag::wait` | 位于 +0x78，**外面有循环**（+0x350 回跳到 +0x5c） ⇒ 醒来后会重新判断条件、能退出 | 同样有循环（+0x364 → +0x5c） |
| **`DapSwEffectImpl::process()` 的 `EventFlag::wait`** | — | 位于 +0x50，**函数体内没有任何回跳覆盖它** ⇒ **一次性死等，醒不来就没有第二次机会** |

**读法（这是事实层，不是猜测层）**：

1. 两库的**销毁骨架完全一样**（都是"发 wake + join"）⇒ 21.1 里"它没调 wake"那句撤回是对的，销毁代码没缺步骤。
2. 差别在**工作线程等的是什么**：音量库的等待在循环里，被唤醒后会重新判断并退出；**杜比 DAP 自己重写的 `process()` 里是一次性的 `EventFlag::wait`，函数体里没有回跳**。⇒ 只要那一次等待没被**正确的那把 flag** 叫醒，这条线程就永远停在这里，`join()` 永远不返回。
3. 这与崩溃现场完全对上：tombstone 里两条 `DAPV3` 停在 `DapSwEffectImpl::process()+80`（偏移 0x50 附近，正是这条一次性 wait），而 `Music Volume L` 的等待能被正常收回（安全态实测 1 毫秒销毁完成）。

**所以终判的准确表述是**：不是"销毁代码漏了唤醒"，而是"**DAP 重写的处理函数里有一次性死等，销毁路径发出的唤醒叫不醒它**"。⇒ 缺陷在杜比这层封装库内部，**配置层、脚本层都碰不到它**；能改的只有替换这个库，而全盘扫描证明设备上只有这一份（`/system /system_ext /product /vendor /odm /apex` 全扫无第二份）。

**顺带纠正一处旧表述**：十九节说"多实例 + 无人唤醒的 FMQ 等待"——"无人唤醒"这句现在有了准确版本：**唤醒发了，但发给的不是那条一次性死等所等的那把 flag**。

## 二十二、乙方案取证：原厂杜比到底由谁挂载——答案是系统侧的 Dolby 官方服务，不是配置文件

按用户"乙方安"执行。全程离线只读（解 45G 原包 + 设备只读核对），设备零改动。完整证据见 `04_日志与分析/喇叭排查_20261124/18_乙方案取证_原厂杜比调用方.txt`。

**先纠正一条包结构认知**：ZUI 原包的 `super_N.img` 与分区**一一对应**（`super_4`=system_a 13.2G、`super_6`=system_ext_a 572M、`super_7`=vendor_a），且都是 **ext4**；7-Zip 可直接列目录、抽单个文件，**不用整包解出，也不用解析文件系统**。这次只抽了 4 个件（约 4.7MB）就拿到了答案。

**取证结论四条**：

1. **原厂不靠配置挂杜比**。ZUI 的 `/system/etc/audio_effects.xml` 是 AOSP 默认版（无杜比）；vendor 侧 `sku_canoe/audio_effects_config.xml` 只 apply `dlb_music_listener`、**从不 apply `dap`**。真正在位的是 **`system_ext/priv-app/daxService/daxService.apk`（`com.dolby.daxservice`）+ 它的 privapp 授权 xml + `/system/lib64/libdolbyeffect.so`/`libdolbyproxyandroid.so`/`libdolbyui.so`**。

2. **原厂把 DAP 挂在"全局输出混音"上，只建一个实例**（dex 原文：`Creating a DolbyAudioEffect to global output mix!`、`Dolby service client initialized, create and enable global effect.`、`Create the effect with control priority 1`）。⇒ 与我们配置法造成的"按会话各建一份"是两种生命周期。

3. **原厂自带 audioserver 看门狗，音频服务一起来就 `release()` 再按需 recreate**（`AudioServerWatchDog`、`audio_server_started::dolbyAudio.release()`、`Dax effect recreate successfully`、manifest 注册 `audio_server_restarted` 广播）。⇒ **这正是上次崩溃里缺的那一步**：销毁时机由应用掌控、实例数恒为 1，而不是留给框架在会话销毁时去 close 一个叫不醒的工作线程。

4. **档位与调教走原厂通道**：`content://settings/global/dolby_dap_profile`、`dolby_effect_equalizer`、`setSelectedTuningDevice(default_internal_speaker / speaker_game / headphone_game / default_headphone)`、`/vendor/etc/dolby/dax_geq.xml`。⇒ **顺带解开了十九节前的一个悬案**：`speaker_landscape`/`speaker_portrait`/`speaker_game` 这几套调教"没有调用方"——调用方就是 daxService 的 `setSelectedTuningDevice()`，C17 上因为没这个应用才没人调。

**C17 现状对照**：vendor 侧杜比件**全部在位**（`libswdapaidl.so`、`dax-default.xml` 9 档、DMS 服务 `vendor.dolby.dms.IDms/default` → **found**）；缺的**全是系统侧件**，且已从原包取到本地。`dolby_dap_profile` / `dolby_effect_equalizer` 两个 global 键在 C17 上都是 `null`。

**由此出现第三条路（记为丁方案）**：把原厂 `daxService` 那套系统件装进 C17（systemless 模块：priv-app + 授权 xml + 三个 .so），让**原厂服务用它自己的方式**创建全局杜比效果，档位改走 `global/dolby_dap_profile`，不再用我们的 bind mount 与 sqlite 改库。

**这条路的代价与风险（讲在前面）**：

- 装系统 priv-app 比改配置**更重**，属系统层改动，必须走模块 + 可一键回滚；
- ColorOS 自己的 `AudioEffectCenter` 可能抢同一个全局会话，两者行为需要实测；
- 杜比底层还是同一个 `libswdapaidl.so`，**不能保证不再命中那个一次性死等**；但同一套 vendor 库在原厂 ZUI 上长期不崩，说明原厂形态是被验证过的安全组合；
- 验证必须一次到位：音乐长播 + **抖音高频切流** + 静置空闲三类场景全覆盖，并盯 tombstone，任一类崩即回退（这是上次踩过的坑，不再犯）。
