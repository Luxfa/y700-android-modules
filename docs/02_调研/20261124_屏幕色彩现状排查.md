## 二、当前实际生效的色彩状态（已证，重点）

1. **色彩模式 = NATIVE(0)**。SF：`Current color mode: ColorMode::NATIVE`；`supportedColorModes=[0,7,9]`（NATIVE/sRGB/P3）；`dumpsys display`：`colorMode 0`、`mActiveColorMode=0`、`mDefaultDisplayDefaultColorMode=0`。
   ⇒ **没有做任何色域管理**，面板按原生色域直出。上面那 7 套按色彩模式准备的校准表，**当前一套都没被选中**。
2. **所有图层内容色空间都是 sRGB**：SF 逐层 `dataspace=V0_SRGB (142671872)`、`hdr metadata types=0`、`colorTransform` 全为单位矩阵；`numHdrLayers(0)` ⇒ 当前无 HDR 内容在跑。
   ⇒ "sRGB 内容 + NATIVE 直出"是红色/肤色过艳的经典组合。**这是标准推断，本机未用色卡或实拍验证。**
3. **QCOM 侧也没切色域**：`Current Color Mode: gamut 255 gamma 255 intent 0 Dynamic_range SDR`（255=未指定/自动）。
4. **色彩管理框架是开的**：`ro.surface_flinger.use_color_management=true`、`has_wide_color_display=true`、`has_HDR_display=true`、`wcg_composition_dataspace=143261696(0x88A0000)`（该枚举含义**未核**，不据此下结论）。
5. **护眼/色温当前未施加任何变换**：`dumpsys color_display`（OPLUS 版）显示 `RgbAnimator currentRGB={red=1000,green=1000,blue=1000,protectCoeff=0}`、`ColorRampAnimator currentCCT=7900`、`MatrixConverter stateCCT=7900.0 modifierCount=1 [0] OplusFeatureReadMode`、`ReadMode mIsReadModeOpen=false`、Night display `Activated:false`（temp 2850 未启用）。
   ⇒ 但设置库里留着记忆值：`oplus_customize_custom_eye_protect_enable=1`、`eyeprotect_progress_value=58`、`eyeprotect_cct=7900,0,7900,4296,1`、`color_temperate_ball_mode=2`、`access_color_setting=-1`。**滑条记忆值 ≠ 生效值**，当前实际是"不偏色"。
6. `oplus_last_color_mode=12`（system 设置）与底层 NATIVE(0) **不一致**。**12 是哪一档、谁写的：未证**（需读 ColorOS framework 枚举）。

# 补充（18:3x–19:0x）：三档机制、发黄根因、以及"降饱和"这条路的结果

## 六、三档色彩模式的真实映射（用户实时切档取证）

| 档位 | OPLUS colormode | setColorModeExt | SF colorMode | composer(STC) 应用 | 校准 LUT | LUT 端点 |
|---|---|---|---|---|---|---|
| 标准 | 10 | 301 | **9 = DISPLAY_P3** | `gamut 12 gamma 1 intent 1` | **加载** | 红 `255 0 0→256 3 0`；白 `4095³→4095 4030 3724` |
| 自然 | 11 | 303 | **7 = SRGB** | `gamut 1 gamma 1 intent 1` | **加载** | 红 `255 0 0→218 11 3`；白 同上 |
| 鲜明 | 12 | 307 | **0 = NATIVE** | `gamut 255 gamma 255 intent 0` | **不加载** | — |

调用链：`Settings key_color_mode` → `ColorDisplayService$2.onChange` → `onDisplayColorModeChanged` → `DisplayTransformManager.setColorMode` →（同时）`setColorModeExt 3xx` → composer `SDMColorModeStc::ApplyCurrentColorModeWithRenderIntent` → `StcMotoColor ProcessOps` 加载 3D LUT → `HWDeviceDRM::SetMotoPAHsic [hue=0 saturation=0 value=0 contrast=0]`。

**更正记录**：本文 §二.1 曾写"色彩模式切换没落地"——**错**。取证时用户正停在"鲜明"档，而鲜明档按设计就是 NATIVE 不处理，采样点选错导致误判。三档切换**确实落地**，只是不走 SF 标准色彩模式以外的通道。

## 七、"标准/自然发黄"的根因（已证，且不是故障）

- 实际生效的 3D LUT **不来自 `/vendor/etc/display/`，而来自 `/mnt/vendor/persist/display/`（逐机出厂标定）**。判据：运行日志打印的白点终点 `4095 4095 4095 → 4095 4030 3724` 与 persist 两份 cali 文件的末行**完全一致**；/vendor 那份是 `4095 4071 3788`，**不匹配**。
- persist 标定把白点蓝通道压到 `3724/4095 = 90.9%`、绿 98.4%、红 100% ⇒ **白场确定性地偏暖**。
- 这是**校色目标本身**（把面板校到标准白），不是设置错乱；"鲜明"档因为没有标定，白点回到面板原生（偏冷）且色域溢出（偏艳）。**所以"艳+冷"与"准+暖"是同一件事的两面。**
- 红线遵守：`persist` 属不可逆区，**本轮只读取证，未写一个字节**。

## 八、"降饱和 10%"三条路的实测结果

| 路 | 做法 | 实测结果 |
|---|---|---|
| 软件全局饱和 | `cmd color_display set-saturation 90` | **无效**。状态位翻成 `Activated: true`，但 SF 全量 **232 个图层 colorTransform 仍是单位矩阵** ⇒ 没产生任何色彩变换。已复原 100。（我先前"旋钮是真的"的判断只看状态位，过头，已撤回） |
| 启用被关的颜色服务 | `setprop ctl.start vendor.qti.hardware.display.color-service`（用户授权） | **服务成功启动、两接口注册、无 SELinux 拦截**，但 AIDL v1 只有 6 个方法：`init / deInit / getRenderIntentsMap / getSPRMode / setSPRMode / toggleSocketService` —— **没有饱和度入口**。已 `ctl.stop` 复原（`stopped`，接口回到 not found）。 |
| 改 STC 参数表 | 读 `/vendor/etc/display/moto_stc_profile.xml` | **文件不存在**（字符串编译进 `libstcMotoColor.so`，但机器上没这份表）⇒ HSIC 全 0 是硬编码默认，无表可改。 |

**剩余唯一硬件通道（未做）**：`toggleSocketService(true)` + `/vendor/bin/qdcmss`（`QDCMSocketService`/`qdcmsocket`）——厂商 QDCM 上位机协议通道，能下发 HSIC/PCC/3D LUT。要用它得**逆向 QDCM socket 协议**，成本高、且属厂商调试面，未获授权前不动。

## 九、因此现在能给的零工程解法

**用"标准"或"自然"档拿到校准（艳度自然回落），再用 ColorOS 自带的色温滑条把白点往冷调**，抵消出厂标定的暖白（framework 里那张表支持 CCT 2700→9345 共 152 档，当前停在默认 7900）。全程系统自带开关、可即时回退、不碰 persist、不启停服务。
