# 社区模块与插件横评（2026-11-26）

> 作者 hutao。方法：三路并行网络调研（框架生态 / 本机机型向 / 性能温控向），未动设备、未装任何东西。
> **本文所有条目都是"外部信息"，没有一条在本机 TB323FU + ZUXOS 2.5.10.055 上实测过**；要用必须先按第八节的流程自己验。
> 来源分级：**〔官方〕** 厂商/上游文档与 release 页　**〔一手〕** 项目仓库 README/release/issue 里带的实测记录　**〔社区〕** 论坛/酷安/B站/贴吧 的口述经验　**〔推断〕** 逻辑推演，无证据。

## 〇、一句话结论

**没有"装了就变好"的现成好模块。** 真正有价值的产出是三条方法论：① 温控优先试厂商自带的 `/data/vendor/thermal/config` 覆盖目录（比 bind mount 干净）；② GPU/CPU 只抬地板、不拆天花板；③ 2025-11 曝出的恶意模块事件说明"来路不明的 zip"是本项目当前最大的实际风险，比任何功能收益都重要。

## 三、性能与温控向（这是第四批的正题）

| 项目 | 原理 | 可用性 | 级别 | 判 |
|---|---|---|---|---|
| **MiThermalScheduler** | 把生成的配置写进厂商自带覆盖目录 **`/data/vendor/thermal/config`**，不碰 vendor 分区；含限帧放宽、应用刷率锁定；写后回读校验、解析失败自动回滚、卸载即还原 | 活跃，小米侧已验 Android 17；**方法论对我们最值钱** | 〔一手〕 | **优先验证这条路**：先查本机 thermal-engine 是否也读这个目录 |
| **g750-boost**（雨色 v2.2.11，2026-09） | 游戏态写 GPU **地板**（`min_pwrlevel` + `gpu_min_clock` + `devfreq/min_freq`），另起四路 0.3s 护栏把被原厂拉低的上限复位；明确适配 **SM8850 / Adreno 840**，频表含 902/222（与我们取证一致） | 活跃，Magisk/KSU/APatch 通用 | 〔一手〕 | **最值得参考的实现**（不覆盖 conf，只抬地板 + 护栏） |
| UniversalThermalFix / Hellish TTD NMX / binmt"移除温控" | 停 thermal-engine 或 HAL、阈值抬到 120–130℃、传感器读数减 30、杀 GOS/Joyose | XDA 帖 403 读不到回帖；无数据，口碑型 | 〔社区〕 | **别碰**（拆天花板，无任何长时可靠性反馈） |
| Uperf（yc9559） | 用户态 hint 调度 | 预置配置止于 8 Gen1，**无 8 Elite/SM8850** | 〔一手〕 | 观望（没有本机配置就等于没效果） |
| 针对 `qapegameconfig.txt` 的公开模块 | — | **检索为空** | 〔推断〕 | 我们若做就是独一份，不必等社区 |

**社区安全边界（MiThermalScheduler 写得最完整，与本项目既有纪律一致）**：保留传感器定义与 BCL 低电量保护；CPU 只设降频下限（抬地板）、GPU 只限降频等级；放宽后的触发温度 ≤ 过热保护温度（默认 50℃）；写后回读校验 + 解析失败自动回滚；卸载即还原。**禁止**杀 thermal-engine（我们 11-23 就吃过：daemon 不会自己接回场景 0，整机在下次重启前没有温控）。

**热关机这条底线拆不掉**〔官方/一手〕：Thermal HAL 的 SHUTDOWN 档由 `thermal_info_config.json` 独立触发，改 thermal-engine 的 conf 不会移除它 ⇒ 过热表现为强制关机而不是烧板。真正的风险是**电池长期 >45℃ 的老化/鼓包**〔推断，无公开个案〕。

## 四、"实打实提升"里哪些是真的、哪些是玄学

| 诉求 | 结论 | 级别 |
|---|---|---|
| 散热背夹 | **收益最确定的一项**：Y700 裸机 30 分钟烤机背温 41–42℃，加磁吸半导体背夹降到 21–28℃（约 −15℃）。热预算一抬高，原厂温控自己就不降频了 | 〔社区实测，B站〕 |
| 官方组合：性能模式 + **旁路充电** + 电池养护 80% 自动旁路 | 直接砍掉"边充边玩"这一路热源，等于免费抬高热预算；本机 11-25 已用 `charging_enabled=0` 实现过旁路充电 | 〔社区实测 + 本机历史实测〕 |
| 画质/帧率解耦（降渲染分辨率、关光追、开原生高帧） | 有效且零风险；本机 11-25 已用官方和平营地"分辨率提升"验证过同类机制 | 〔本机实测〕 |
| `min/peak_refresh_rate`、`device_config put game_overlay` | Android 15+ 游戏默认被压到 60Hz，系统仍会按温度覆盖 ⇒ 只能算"少一层限制"，不是稳赢 | 〔官方〕 |
| **触控采样率模块** | **基本玄学**：采样率由触摸 IC/固件决定，内核通常不暴露可调节点（有仓库实测 `touch_sampling_rate` 不存在）。官方口径也是"按刷新率自动匹配" | 〔一手 + 官方〕 |
| 操作延迟 | 有机理的部分：抬 GPU 地板、绑大核、锁定 `min_refresh_rate` 能减迟滞；其余归调度玄学 | 〔推断 + 一手〕 |
| **听声辨位/空间音效** | 蓝牙链路延迟（>100ms）才是真问题 ⇒ **有线 3.5mm/2.4G 才是解**；手游本身是立体声，系统级"虚拟 7.1"属二次上混，小样本盲测显示**反而让前后定位变糊**；ViPER 类增强属主观玄学 | 〔社区小样本盲测〕 |
| 通用触感/全局高刷/LDAC-aptX/相机类模块 | **没有仍在维护且适配 A16/17 的通用件**，多是机型绑定 vendor 库替换 ⇒ 不碰 | 〔一手 + 推断〕 |

## 五、总判与动手顺序

1. **不装任何"温控绕过"成品**（y700_thermal_boost / TTD 类）——它们拆天花板或伪装读数，与我们的红线和取证结论冲突。
2. **第四批照这条路走**：先验 `/data/vendor/thermal/config` 覆盖目录在本机是否被 thermal-engine 读取 → 若可读，走覆盖目录（零 bind mount、OTA 友好）；若不可读，退回 bind mount conf；两种都**只抬地板、保留末档与 BCL、写后回读、失败自动回滚**。GPU 侧优先复用 g750-boost 的"三通道 + 护栏"写法思路（自己实现，不装它的包）。
3. **零风险项先做满**：背夹 + 旁路充电 + 官方性能模式 + 画质帧率解耦。这些的收益顺序在社区实测里排在所有软件改动前面。
4. **Xposed 类（ZTool/UnfuckZUI）整体观望**：要它们就得先上 Vector，而 Vector 在 A17 上有"管理器在但没注入"的静默坑；且 ZTool 自标最后支持 A16。等 A17 明确适配再说。
5. **属性类改动可以"抄清单不装包"**：UnfuckZUI 那几个 `persist.sys.*` 属性若确认在 ZUXOS 17 有效，我们自己写进模块，比引入一个 LSPosed 依赖面小得多。

## 六、必须记住的安全事件（比功能收益重要）

2025-11 前后酷安/binmt 曝出**恶意模块**：伪装成"终端扩展"，在 `service.sh` 里向 priv-app 注入，窃取短信与微信支付密码；**正规渠道的模块也可能被二次注入，卸载模块后仍可开机复活**，彻底清干净需清空 `/data/adb` 并全改密码。〔社区一手披露，多源交叉〕

⇒ 本项目立规（已同步进技能纪律）：
1. 只从 **GitHub Releases 原文**下载，不从任何"模块商店 App"里点安装；
2. 装之前**解包读 `customize.sh` / `service.sh` / `post-fs-data.sh`**，见到 `curl|sh`、写 `/system/priv-app`、捆绑不明二进制、要求联网的，一律不装并上报；
3. 闭源且要联网的模块默认拒；
4. 兜底手段记牢：卡米用 `adb shell magisk --remove-modules`，或开机前按住音量减进安全模式（Magisk 官方 docs/ota.md、faq.md）。

- 伪装温度（`emul_temp`）：属"伪造传感器读数"，与"不伪造校验结果"同族，**不采用**。

## 九、UI 美化专题（11-26 17:4x 追加，两路并行调研）

### 9.1 先纠我们自己一条错

我们此前在 `20261126_回原厂055可提升面与移植包横评.md` §三 判"dock 6 槽写死 ⇒ UI 面基本没戏"。**静态层证据仍然有效**（`resources.arsc` 的 `numHotseatIcons`、hotseat 布局只到 `hotseat_icon_6`、`is_layout_locked=true`、92 个 RRO 无一针对 Launcher），**但结论过宽**：漏评了"运行时 hook"这条独立路径。社区项目 ZTool 直接 hook `com.zui.launcher` 就做出了"解锁 Dock 应用数上限""允许关闭 Dock""自定义桌面网格""图标大小突破系统 0.6~1.3 倍率""无字模式""大文件夹对齐""批量卸载"。〔一手 README〕
⇒ **缺的那一步**：把"RRO/apk 资源覆盖不了"外推成了"整个 UI 面改不动"。已在原文加更正框。

### 9.2 三条活路（按风险从低到高，建议按序做满再往下走）

| 路 | 能改什么 | 门槛 | 级别 |
|---|---|---|---|
| **① settings/属性级**（零框架、随时可退） | 动画三缩放、字体大小、显示密度、沉浸模式、状态栏图标黑名单 | 无，一条命令 | 〔官方 AOSP〕〔一手实测 A15 仍生效〕 |
| **② RRO overlay** | 颜色/尺寸/布尔类资源（**layout、anim、XML、代码都不行**）；A10+ 目标必须声明 `<overlayable>`，否则被拒 | 先上机 `cmd overlay list` 探 ZUI 到底开放了哪些 overlayable 面 | 〔官方 RRO 文档〕〔推断：ZUI 声明情况未知〕 |
| **③ Xposed 载体 + ZUI 专属模块** | Dock/网格/图标大小/控制中心磁贴/状态栏时钟与网速/锁屏时钟颜色/充电动画/亮灭屏过渡动画/自定义字体/一视界分屏策略/浮窗侧边栏 | **必须先解决载体**：Vector 在 A17 上正式版有"管理器在但不注入"实锤（`IPackageManager` 签名变化），要 canary/debug 版，且 v2.1 有 R8 合并 XResources 导致 system_server hook 全失败的 bug（v2.2 已修） | 〔一手 release notes〕〔社区 XDA 实测〕 |

**可立即用的 ① 清单**（本机未验，逐条单独验）：
```
settings put global window_animation_scale 0.5        # 三件套：window/transition/animator
settings put global transition_animation_scale 0.5
settings put global animator_duration_scale 0.5
settings put system font_scale 1.15                   # 改前先 wm density 读回原密度
wm density <原值>                                      # 显示大小，改错会糊整屏，先读后写
settings put global policy_control immersive.full=*   # 沉浸；A15+ 底部上滑仍会探头；恢复用 settings delete
settings put secure icon_blacklist ...                 # 隐藏状态栏图标，随安全补丁可能失效
```
〔出处：AOSP 开发者选项同源；policy_control 有 A15 现场排查实测；icon_blacklist 属社区口径〕

### 9.5 载体门槛（③ 的前置，也是最容易白干的一步）

装任何 ZUI 专属模块前，**必须先证明 Xposed 注入真的发生**，不能只看"管理器里显示已启用"：
1. 选 **Vector**（LSPosed 原版停更且 A15 上可让 Zygisk 整体失效）；A17 需要 **canary/debug** 版（正式版有"管理器在但不注入"实锤，成因是 `IPackageManager` 签名变化）。
2. 验注入：`logcat` 里要有 `Loading Vector/Xposed` 之类的加载记录，**且目标进程内要能看到 hook 生效的行为差异**；只看开关状态 = 未验证。
3. 版本坑：v2.1 有 R8 合并 `XResources` 导致 system_server 全部 hook 失败的 bug，v2.2（2026-08-04）已修 ⇒ **别装 v2.1**。
4. 载体本身也是第三方代码：**按第六节安检逐行读它的 `service.sh`/`post-fs-data.sh`**，并记住"只从 GitHub Releases 原文取"。

### 9.6 风险与自救（UI 类特有的炸法）

- **字体模块**：`fonts.xml` 路径或文件名写错 ⇒ **卡在开机动画**（lxgw 模板 README 明确警告，且指出各 OEM 配置路径不同需手改）。〔一手〕
- **hook SystemUI 的模块**：hook 失败 ⇒ SystemUI 反复重启 / 设置页闪退（Vector v2.1 就是典型）。〔官方 release notes〕
- **ZTool 自曝的 OOBE 检查失败** ⇒ 可能**卡开机向导**，这条对本机最危险（我们刚刷完机，重装时一定会走 OOBE）。〔一手 changelog〕
- 自救链（按顺序，都不需要重刷）：Magisk 内"移除"模块 → `adb wait-for-device shell magisk --remove-modules`（**我们已有开机常驻无线 adb，这条比多数人好执行**）→ 安全模式（开机动画后长按音量减，Magisk 自动禁用全部模块且状态跨重启保留）→ Recovery 里改名 `/data/adb/modules` → 9008 线刷。〔社区多篇一致 + Magisk 官方 docs〕
- OTA 提醒：A/B 机型 OTA 会把 root 冲掉（需"安装到未使用槽位"流程）；**模块挂的 system 资源与新版错位是 OTA 后 SystemUI 闪退最常见原因** ⇒ 我们的 `com.lenovo.ota` 停用状态要保持住。〔社区〕

### 9.7 建议顺序（未开工，等裁定）

1. **先做满 ①**：动画三缩放 0.5 + 字体/显示大小按需微调——零风险、当天见效，"手感"收益其实最大。
2. **再探 ②**：上机跑 `cmd overlay list`，把 ZUI 真正开放的 overlayable 面列出来（这是**一手取证**，能一次性判死或判活整条 RRO 路线，成本十分钟）。
3. **③ 只在两个前提都成立时才开**：Vector 在本机 A17 上**验到注入成功** + ZTool **明写支持 A17/ZUXOS 2.5**。二者任一不成立就不开这条线，避免"装了没生效"或撞 OOBE 坑。
4. 换第三方桌面：**判死，不做**。
