## 0. 一句话结论

**能复原。** 但可复原的不是 `lastkmsg.log`，而是同一份 ramdump 里一直没人看的 `md_KLOGBUF.BIN` / `md_KBOOT_LOG.BIN`——它们是**触发 900E 那一遍启动（03:17 用 9008 写入 init_boot 的 Alpha 补丁）的完整内核日志**，从 `0.000000` 一路到 `Kernel panic`＋看门狗咬狗，共 2721 条记录、环形缓冲只用 38.8%（**没绕圈 ⇒ 日志完整**）。
`lastkmsg.log` 本体则是**上一次启动（uptime 480–511 s，ColorOS 框架真正跑起来那一遍）的 pstore/ramoops console 尾巴**，属于不可逆的有损读取，只能"降噪读"，不能逐字复原。

## 2. lastkmsg.log 损坏形态判定（四项测试全做过）

基线：`lastkmsg.log` 17,010,192 B，非可打印字节 12,919,476 = **75.95%**；但只取 console 实际所在的 `0xc204000c..0xc2050000`（64 KiB）窗口，非可打印只有 **11.87%**——即"17 MB 里只有开头约 64 KB 是真日志"，其余是越界抓到的无关内存（`0x40000` 之后直接是 `0xff`/`0x00` 填充，见 `an1_corruption.py` 分块统计）。

| 测试 | 做法 | 结果 | 判定 |
|---|---|---|---|
| ① 2/4 字节去交织 | stride 2/3/4/5/6/8 分道，算各道可打印率 | 全部 0.872–0.888，无任何一道接近 1.0（`an7_lastkmsg_tests.py` [1]） | **否**：不是周期性交织 |
| ② UTF-16LE/BE | 统计两条道上的 `0x00` 占比 | 偶道 132/8192、奇道 140/8192（1.6%），ASCII 的 UTF-16 应约 50% 零字节；解码直接抛异常 | **否**：不是 16-bit 文本 |
| ③ 用 `md_KDMESG.BIN` / `dmesg_dumps.bin` 里的原始 logbuf 替代 | 扫两文件的 logbuf/文本 | `0xff` 占比 81.7% / 82.8%，可打印串（≥40 B）**0 条** | **否**：该 oops 区压根没被写过 |
| ④ 按 load.cmm 地址回 DDRCS 取真 last_kmsg | `DDRCS0_0.BIN` 偏移 `0x4204000c` 读 64 KiB 比对 | **65536/65536 完全相同** | **否**：没有更干净的副本，文件＝内存原样 |

真正的损坏形态（三条互相印证的证据）：

1. **可打印字节里的坏字节，77% 是"最高位被强制成 1"**：`0xe3&0x7f='c'`、`0xf5='u'`、`0xba=':'`。整窗做 `b&=0x7f` 后，可打印率 **0.881 → 0.9727**（`an8_bit7.py`）。⇒ 通道是**位翻转**（bit7 / bit6 为主，bit6 翻转表现为大小写互换：`vendoR`、`Wengor`）。
2. **同一物理地址两次抓取互不相同**：`md_KDMESG.BIN` 与 `dmesg_dumps.bin` 都声称来自 `0xc2000000`，64 KiB 重叠区只有 **86.05% 字节相同**（`0x1:64 vs 66`、`0x2:67 vs 07`、`0x3:5b vs 53`…）。⇒ 错误发生在**读取/传输路径**，非确定性、不可逆推。
3. **另一种伪影是"尾部字节被重复"**：`md_KLOGBUF.BIN`（同一 dump 里）几乎每条记录末尾多出 1–2 个字符：`...started at EL1L1`、`...activated.d.`、`max_idle_ns: 7645041785100000 nsns`、`...linear)r)`。按"末 k 字符与 k=1..2 重复即删"的规则，2721 条里 1921 条可自动修回。

⇒ **结论：lastkmsg.log 无法逐字复原**（有损位翻转＋字节重复，同地址二次读取都不一致）；能做的是"降噪读"：产物 `prevboot_console_bitmasked.txt`（bit7 屏蔽后的 64 KiB），结构完整、时间戳与关键词可辨，个别字母错。

## 6. `logcat.log`（2228 B）时间线对齐

* 来源＝pstore **pmsg**（用户态 `/dev/pmsg0`）尾段，phys `0xc208000c`，非文本而是**二进制 logger 记录**（这是它"看起来像垃圾"的原因，不是损坏）；同区已含 bit7 伪影（可打印率 63.9% → 屏蔽后 73.5%）。产物：`logcat_bitmasked.bin`。

## 8. 局限（明确写清失败项）

1. `lastkmsg.log` 的 64 KiB 之外全是越界抓来的无关内存（`0xff`/`0x00`/GPU 内核符号 `_SCK_Stp_func_syncpoint_Fence...`），没有日志价值，也不再尝试复原。
2. 去交织（stride 2–8）、UTF-16、`md_KDMESG`/`dmesg_dumps` 替代、DDRCS 定点回读 **四条复原路线全部试过并证伪**（数据见 §2 表）；同址两次读取 86.05% 一致，说明通道本身非确定性出错，**逐字复原在信息论上不可能**，只能做 bit7 降噪＋模板判读。
3. `md_LOG_DESC` / `md_LOG_INFO`（16384×24 / 16384×88 数组）未能解出逐条 `ts_nsec`：`md_LOG_INFO` 首记录 16 B 全零后 `37 00 00 c2`（＝`0xc2000037`，指向 ramoops 区）等字段排布与内核 `struct printk_info` 不符，疑为 Qualcomm 私有索引；因此本次时间轴只拿到 `0→0.5496 s`（boot_log 镜像）＋`≈1.0–1.5 s`（ufshcd `last intr at 1038541 us`）两个锚点。
4. 尾部重复伪影的自动修复是启发式（k=1..2），1921/2721 条被改写；个别形如 `res=1=1`、`...0 0` 的合法串无法判定，故保留未修的 `klogbuf_records.txt` 供逐条回查。
5. `avc denied` 的"全集去重计数"对上一遍只能给**下界**（≥83 条 console＋≥112 条 pmsg 片段，两类 name、一个 tclass），因为行数量本身被位翻转打散。
