## 二、已交付并验证的功能

- **自动亮度**【实证，11-24 14:5x 改路线】：**走系统原生自动亮度**（ColorOS DDC 路径）。遮光实测：手掌盖住→亮度 4%、见强光（4119lux）→61%、回室内 91lux→25% 稳定收敛，`mAppliedAutoBrightness=true`。模块 `y700_auto_brightness`（自建执行器）**已从设备卸载**（11-24 用户自打 `remove`，本次开机 Magisk 执行；`uninstall.sh` 已清 pid/win，`mode` 未被还原仍 =1）⇒ 重启后无 daemon 痕迹、原生独占亮度。恢复只能从仓库 `03_脚本与模块/modules/y700_auto_brightness/` 重装，且**重装前必须先改掉 `daemon.sh:97-100` 强制 `mode=0` 那段**，否则症状一（开关自己关）原样复发。停用理由：同一 91lux 模块写 41%、原生写 25% ⇒ 自建执行器长期把屏幕写得比系统本意亮近一倍，是用户"刷视频被拉很高"的根因。**已知代价**：① 游戏期不再锁亮度；② `finalLux` 强阻尼滞后约 70 秒，暗处偶发一次回弹。出处：相位 M1（含 39 样本遮光数据）。
- **英雄联盟手游高帧实测通过**【实证，11-24 17:0x 两局对照】：144Hz 档**满 144 帧**（帧距恒 6.94ms，90 个窗口仅 1 次掉同步，最差 176ms）；同局 60Hz 档帧距恒 16.67ms 但 **63 窗口掉 8 次、最差 433ms**，而该档 GPU 均值占用更低（66% vs 80%）⇒ **瓶颈是 60Hz 档下 kgsl DVFS 升频保守，不是算力不足**；两局热档全程 0。实用解排序：**①帧率直接设 144（零风险）②抬 GPU 频率地板救 60 档（增发热、收益有限）**。出处：相位 N3 §十一。
- **旁路充电 + 充电上限**【实证】：硬件 `bypass_setting` 节点本机不存在 ⇒ 用 `charging_enabled=0`（实测 `Ib=0` 且适配器继续供 1.4–2.5A）实现同效果；接 ColorOS 原生开关；上限 95%/回差 5%；重启自启复验通过。出处：相位 B1 系列。
- **通信共享（拨出/接听/收发短信）**【实证+口述】：ims.apk 链路打通后真实呼叫验证通过；后三项里拨出为实测、其余口述。出处：相位 Y/Z/AA。

- **色彩调节（11-26 定稿，原厂 055）**【实证】：**不需要 bind mount、不碰 vendor**。`y700_display_tune`（ColorOS 版）依赖的 `settings put --put package:display --key synergy_*` 在原厂系统直接报 `Invalid namespace '--put'` ⇒ 原样搬回是空转，**判死不搬**。原厂等价载体与定稿值：**①饱和度** = 档位 `system:screen_tone_saturate_mode=1`（标准0/鲜艳1）+ **连续覆盖 `cmd color_display set-saturation 95`**（0-100 可用，100 等于无覆盖；覆盖是运行时的，重启丢 ⇒ 由模块 **`y700_color_tune` v1** 开机重放）；**②色温** = `secure:general_color_temperature="R,G,B"` 增益，定稿 **`1.0,0.994,0.987`**（半档暖再退半步，settings 持久；**v1 曾故意不重放以免顶掉用户自行修改，v2 起按用户"存成档位"的要求改为随档位重放**）。**硬判据**：`dumpsys SurfaceFlinger` 的 `colorTransformMatrix` 对角线（定稿态实测 0.963/0.978/0.938）——饱和度与色温都汇到这一个矩阵，settings 写了但矩阵没变就是没生效。**物理限制**：要变冷只能压红/绿留蓝 ⇒ **越冷必越偏青**，"冷而不蓝"做不到（只能连蓝一起降、代价是变暗）；纯白 `1.0,1.0,1.0` 在 14% 亮度下用户判"刺眼"。**已按用户要求做成"档位"，并按 A 方案收敛到 v3**：真值统一存 `/data/adb/y700_color/profile.conf`，切换器 `03_脚本与模块/色彩档位/color_profile.sh` 提供 `soft`（色温 `1.0,0.993,0.985`+饱和 92（17:2x 再校，§一百二十四），**当前定稿**）/`std`（中性+100，等于原厂）/`manual`（停用重放、交还设置页）/`now`（只读复验）。**分工（重要）**：切档位时两样都写一次（= 用户主动动作），但**开机重放只补饱和度**——因为实测证明 ①饱和度中间值**原厂无处持久**（改值后三张 settings 表 0 键变化、dumpsys 无键名、无障碍侧亦无 saturation 键），②色温是系统设置项**自己会留着**，重放只会顶掉用户后续修改。⇒ **模块不能再管色温**。**【11-26 17:1x 真重启复验通过 ⇒ 结案】**：重启后 ①`Activated: true` ②色温仍是 `1.0,0.994,0.987`（原生持久这条判断被证实）③日志有"饱和度 95 就位（第 1 次，rc=0）"，上屏矩阵连读三次恒 `0.962/0.980/0.941`。**新记法：SF 矩阵要连读两次一致才算数**（第一次读到的 0.985/0.989/0.970 是模块落地前的中间态）。出处：流水账 §一百一十九~§一百二十三。

## 十一、喇叭音效基线（20:3x 新立，覆盖"monoPipe 疑似下混"的疑判）

1. **硬件是立体声双扬声器**：I2C 上两颗 `aw882xx_smartpa`（Awinic 智能功放，左右各一）+ `haptic_hv_l`/`haptic_hv_r` 双马达。声卡 `canoe-qrd-snd-card` 为 QRD 参考设计变体，Linux 侧 codec 只有 `lpass-cdc` + `wcd939x`。
2. **功放不走高通 WSA**：WSA884x 未注册（dmesg 无、ALSA 324 控件无任何 spk/amp 项），控制面在 ADSP/I2C（`glink-i2c`）。⇒ **tinymix 查不到扬声器控件是正常现象，不得当成故障证据。**
3. **立体声没有被下混（正式结论）**：主输出 `AudioOut_D` = 2 声道 / mask `0x3`、mixer mask `0x3`，HAL profile 全为 `LAYOUT_STEREO`，8 条线程无 mono，`Master mute: off`、无障碍单声道未开。dump 里的 `monoPipeWritten/PipeSink frames written` 是**厂商管道计数，不是下混证据**；此前"疑似下混"疑判作废。
4. **音效层实际是空的（移植结构性缺口，与色彩 4 个 HAL 缺口同构）**：ColorOS 声明 `audiox_merge`/`speaker_geq`/`high_quality`/`speaker_clean=true`，但 vendor 22 个 soundfx 库无一个 OPLUS AudioX、`libasphere.so` 文件缺失；`/system/etc/audio_effects.xml` 引用的 `music_post_proc`/`voice_post_proc`/`notification_post_proc` **两个分区都未定义**（底层实际给 `*_helper` 一套）。运行时 **8 条输出线程 7 条 0 效果链**，唯一一条是 Dolby 被动音量监听。⇒ **外放无实质软件音效；不要指望设置里的音效项有效果。**
5. **音色归属**：ACDB 命中 `canoe_qrd`（非 `canoe_qrd_wsa884x`），EQ/限幅/保护参数是**联想原厂调音**，不是 ColorOS 音色。音量曲线为 AOSP 通用 `DEFAULT_DEVICE_CATEGORY_SPEAKER_VOLUME_CURVE`。
6. **配置模板残留（事实，不作因果结论）**：`mixer_paths_canoe_qrd.xml` 的 `<path name="speaker">` 为空，`speaker-mono(-2)` 写的是本机不存在的 `WSA PCM CHx MUX`/`SA1 FU21 …=72/84`；`mcs_defs_canoe_qrd.xml` 残留 `WSA`/`WSA2` 各 2 处。
7. **空开关**：`ro.oplus.audio.support.low_latency_game_effect=false` 但 `.show_ui=true` ⇒ 设置里的"游戏低延迟音效"底层不支持。
8. **红线不变**：`persist`/`modemst*`/`frp` 不进写面；音效改动若需写 ACDB 或分区，一律先请示。详见 `02_调研/20261124_喇叭音效现状排查.md`，证据 `04_日志与分析/喇叭排查_20261124/`。

   - **两条立为规矩的前置检查**：① 凡说"已回退/已禁用"，判据必须是**运行态**（`/proc/mounts` 挂载数、包可见性、HAL 内 DAPV3 线程数、crash 缓冲区计数），不能只看标记文件存不存在；② **移植任何系统 priv-app 之前，先用 `dumpsys package permissions` 查它申请的每项受限权限的 `prot=`**，凡 `signature` 而不带 `privileged` 的，白名单救不了，直接判死不开工。
   - 证据与处置：`04_日志与分析/操作流水账.md` §四十五；`03_脚本与模块/丁方案_原厂杜比服务_施工单.md` 第〇节；回退脚本已改为 `disable`（`03_脚本与模块/y700_rollback.sh` 头部写有三个标记名语义）。23:32 复验安全态：挂载 0 / 包不可见 / DAPV3 全 0 / 本次开机 audioserver 崩溃 0 次。

7. **方法论（本轮三次踩坑，下次直接照抄）**：① 判据工具本身要先验证可用（设备无 `sqlite3`，须拉回 PC 读；`logcat -d -t N` 窗口太短会取到空值）；② 空结果先怀疑采样窗口/命令本身，不先怀疑结论；③ 推断未测不得讲成结论（我"不断音"被用户耳朵证伪）；④ 脚本里"取值"与"等待"混在一条调用中会因参数先求值而**整体错一格**，数据看起来仍然合理，最难发现；⑤ **只在单一应用场景测通就宣布"常驻可用"是错的**——杜比方案在音乐应用下全部实测通过，却在抖音（高频重建播放会话）下把音频服务搞崩。交付类改动必须覆盖**至少两类真实场景**（长播放 + 频繁切流）再下结论。

## 十四、蓝牙耳机"电流声"根因结案（11-26 10:1x 新立，长期有效）

- **现象**：蓝牙耳机刷抖音出现两次电流声（用户 11-26 凌晨口述）。
- **根因【实测 + 用户复现确认】**：ColorOS 的**蓝牙空间音效通路**引入杂音。渲染器是高通的 `QTI Spatial Audio Renderer (quasar)`（`ro.audio.spatializer_type=oplus`），**与杜比无关**。用户在 设置→声音与振动→空间音效 关闭后复测不再出现 ⇒ 结案。
- **为什么会被挂上【实测】**：音频策略把蓝牙输出声明为支持空间化 —— `1. "a2dp output"; 0x40000 (AUDIO_OUTPUT_FLAG_SPATIALIZER)`，于是每次路由更新自动走 `Enabling Spatial Audio since enabled for media device bt_a2dp` + `Setting spatialization level to: 1`。
- **加重条件【实测，仅解释易发性】**：SPATIALIZER 线程固定 48kHz/PCM_24_BIT_PACKED，而抖音同一进程 44100 与 48000 混用 ⇒ 每条视频切换都伴随重采样+空间化+头追。
- **已排除【实测】**：USB3 干扰 2.4G（数据线 `DISCONNECTED`、`usb/online=0`）；audioserver/蓝牙崩溃（crash 缓冲命中 0）。
- **状态判据（照此读，别再猜）**：`dumpsys audio | grep -a mHeadphoneSpatializerState` ⇒ `false` = 耳机空间音效已关。`enabledAvailable.first` 是**外放**那一路，与耳机无关（10:10:32 实测耳机路 false、外放路仍 `Enabling Spatial Audio`）。**三张 settings 表里搜不到任何 spatial/dolby/immersive/headtracking 键** ⇒ 偏好存在 OPPO 自己的声音设置里，**不得用 settings 键判状态**。
- **不做**：不为此写模块、不自动强关（手动关已足够，且无证据表明系统会自行回开）。持久性待一次自然复验，见 §四 第 16 条。
