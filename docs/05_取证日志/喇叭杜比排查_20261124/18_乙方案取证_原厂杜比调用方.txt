二、daxService 干了什么（classes.dex 1,978,092 B 字符串取证，逐条原文）

  1) 创建方式——**挂在全局输出混音上，只建一个实例**：
       "Creating a DolbyAudioEffect to global output mix!"
       "Dolby service client initialized, create and enable global effect."
       "initDaxSettings(): Create the effect with control priority 1"
       "setDaxSettingsForUser(): Create the effect with control priority 1"
     类：Lcom/dolby/dax/DolbyAudioEffect;  Landroid/media/audiofx/AudioEffect;
     ⇒ 与我们那次"每个播放会话各建一份 DAP"完全不同：**原厂是 session 0 全局单实例**。

  2) **自带 audioserver 看门狗，重启时先释放再重建**（这正是我们缺的那一步）：
       Lcom/dolby/daxservice/AudioServerWatchDog;
       "audio_server_started::dolbyAudio.release()"
       "initDaxSettings::dolbyAudio.release()"
       "Dax effect recreate successfully"
       manifest 里注册的广播：audio_server_restarted、com.dolby.intent.ACTION_RELOAD_TUNING、com.dolby.intent.action.DAP_PARAMS_UPDATE
       "Dolby service has died, try to reconnect 1s later." / "Reconnect Dolby service reached MAX retry times, abort..."
       "Dolby audio effect is out of control in audio_server_started"
     ⇒ 原厂把"效果对象生命周期"当成一等事务管：**音频服务一起来就 release()，再按需 recreate**，
       绝不让效果对象在会话销毁后悬着——我们的配置挂载法做不到这一点（生命周期归框架）。

  3) 档位与调教走**原厂通道**，不是我们改的 sqlite 库：
       "content://settings/global/dolby_dap_profile"
       "content://settings/global/dolby_effect_equalizer"
       "dolby_on_off default_internal_speaker"
       "setSelectedTuningDevice speaker_game" / "headphone_game" / "default_headphone" / "default_internal_speaker"
       "/vendor/etc/dolby/dax_geq.xml"（均衡器参数文件，读不到也容忍）
     ⇒ **之前查"横竖屏/游戏调教没人调用"的答案出来了：调用方就是 daxService 的 setSelectedTuningDevice()。**
     ⇒ C17 上 `settings get global dolby_dap_profile` 与 `dolby_effect_equalizer` 都是 **null**（ColorOS 不写这两个键）。

  4) 它对接 DMS HAL（AIDL 与 HIDL 两条都试）：
       Lcom/dolby/daxservice/hal/DmsHal; /DmsHalAidl;/DmsHalHidl;  Lvendor/dolby/dms/IDms$Stub$Proxy;
       "Cannot get AIDL DMS" / "Cannot get HIDL DMS" / "Cannot create DMS HAL instance via either AIDL or HIDL impl."

四、这条路与我们上次崩溃的关系（为什么值得一试）

  上次的死法：配置法让框架**按会话**创建 DAP，会话一销毁框架就调 close()，而 DAP 的工作线程停在
  一次性 `EventFlag::wait` 上叫不醒（见 16_机器码复核），于是 join 不返回 → 看门狗杀 audioserver。
  原厂法：全局单实例 + 音频服务重启即 release/recreate ⇒ **销毁时机由应用掌控，且实例数恒为 1**。
  同一套 vendor 库在原厂 ZUI 上长期不崩，说明原厂这条路径是**被验证过的安全形态**。
  风险（不得隐瞒）：C17 的系统侧是 ColorOS，daxService 与 ColorOS 的 AudioEffectCenter 可能抢同一个
  全局会话；装系统 priv-app 本身是比配置挂载更重的改动；仍需真机验证（含抖音高频切流）。
